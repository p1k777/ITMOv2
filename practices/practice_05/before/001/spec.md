# Feature Specification: Сортировка задач (backend)

**Feature Branch**: `001-tasks-sort-back`

**Created**: 2026-11-01

**Status**: Draft

**Input**: User description: "Создай спецификацию логики сортировки задач в приложении TaskHub. Расширить метод Storage.list_tasks() параметром sort_by и sort_order. sort_by: title, status, due_date, created_at, tags, None. sort_order: asc/desc. Стабильная сортировка, без новых зависимостей."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Сортировка задач по выбранному полю (Priority: P1)

Пользователь GUI (или внутренний вызов) запрашивает список задач с сортировкой по выбранному полю. Система возвращает задачи, отсортированные по возрастанию или убыванию указанного поля, после применения всех фильтров.

**Why this priority**: Без сортировки пользователь не может быстро найти нужную задачу в списке из десятков или сотен записей. Сортировка — базовая возможность для навигации.

**Independent Test**: Запросить список задач с параметром сортировки и проверить, что возвращённый список соответствует ожидаемому порядку.

**Acceptance Scenarios**:

1. **Given** список из 5 задач с разными названиями (включая кириллицу), **When** запрошен список с сортировкой по "title" (asc), **Then** задачи возвращаются в алфавитном порядке, без учёта регистра, с корректной обработкой кириллических символов
2. **Given** список задач со статусами "todo" и "done", **When** запрошен список с сортировкой по "status" (asc), **Then** задачи со статусом "todo" идут перед задачами со статусом "done"
3. **Given** список задач с разными значениями due_date и одной задачей без даты, **When** запрошен список с сортировкой по "due_date" (asc), **Then** задачи с датой идут по возрастанию, задача без даты — в конце списка
4. **Given** список задач, созданных в разное время, **When** запрошен список с сортировкой по "created_at" (desc), **Then** задачи возвращаются от новейших к старейшим
5. **Given** список задач с тегами и одной задачей без тегов, **When** запрошен список с сортировкой по "tags" (asc), **Then** задачи сортируются по первому тегу (алфавитно, без учёта регистра), задача без тегов — в конце

---

### User Story 2 - Направление сортировки (Priority: P2)

Пользователь может задать направление сортировки: по возрастанию (asc) или по убыванию (desc). По умолчанию — по возрастанию.

**Why this priority**: Направление сортировки расширяет базовую возможность. Например, для due_date может быть полезно видеть задачи с самым отдалённым сроком первыми (desc).

**Independent Test**: Запросить список задач с сортировкой по "due_date" в обоих направлениях и проверить, что порядок противоположный.

**Acceptance Scenarios**:

1. **Given** список задач с due_date и одной без даты, **When** запрошен список с sort_by="due_date", sort_order="asc", **Then** задачи с датой по возрастанию, задача без даты — в конце
2. **Given** тот же список, **When** запрошен список с sort_by="due_date", sort_order="desc", **Then** задачи с датой по убыванию, задача без даты — в начале
3. **Given** список задач с тегами и одной без тегов, **When** запрошен список с sort_by="tags", sort_order="desc", **Then** задачи с тегами по убыванию первого тега, задача без тегов — в начале

---

### User Story 3 - Сортировка не изменяет хранилище (Priority: P3)

Сортировка применяется только к возвращаемому списку. Порядок задач в файле хранилища не изменяется. Повторный запрос без сортировки возвращает задачи в исходном порядке.

**Why this priority**: Гарантирует, что сортировка — операция, невидимая для данных. Не нарушает контракты хранилища и другие интерфейсы (CLI).

**Independent Test**: Запросить список с сортировкой, затем без — проверить, что второй запрос возвращает исходный порядок.

**Acceptance Scenarios**:

1. **Given** список задач в файле в порядке A, B, C, **When** запрошен список с sort_by="title", **Then** файл не изменяется
2. **Given** предыдущий запрос выполнен, **When** запрошен список без сортировки, **Then** возвращается порядок A, B, C

---

### Edge Cases

- **Пустое хранилище**: Сортировка пустого списка возвращает пустой список без ошибок
- **Все значения равны**: При сортировке по полю, у которого все значения одинаковы (например, все задачи со статусом "todo"), сохраняется исходный порядок из файла
- **Задача без due_date при sort_by="due_date"**: При asc — в конце, при desc — в начале
- **Задача без тегов при sort_by="tags"**: При asc — в конце, при desc — в начале
- **Одинаковые названия (case-insensitive)**: При sort_by="title" задачи с одинаковыми названиями (в нижнем регистре) сохраняют исходный порядок
- **sort_by=None**: Сортировка не применяется, возвращается порядок из файла
- **Один элемент в списке**: Сортировка списка из одного элемента возвращает этот элемент
- **Повреждённый tasks.json**: `list_tasks` propagates исключение из `json.load` (не возвращает пустой список)
- **Недопустимые sort_by/sort_order**: Backend выбрасывает `ValueError` с описательным сообщением

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система должна поддерживать сортировку по пяти полям: "title", "status", "due_date", "created_at", "tags", а также по умолчанию (без сортировки)
- **FR-002**: Система должна поддерживать направление сортировки: "asc" (по умолчанию) и "desc"
- **FR-003**: Сортировка по "title" должна игнорировать регистр и корректно обрабатывать кириллические символы
- **FR-004**: Сортировка по "status" должна размещать "todo" перед "done" при asc; при desc — "done" перед "todo"
- **FR-005**: Сортировка по "due_date" должна помещать задачи без даты (None) в конец при asc и в начало при desc
- **FR-006**: Сортировка по "created_at" должна использовать лексикографическое сравнение ISO-строк (UTC, суффикс Z)
- **FR-007**: Сортировка по "tags" должна использовать первый тег (алфавитно, без учёта регистра); задачи без тегов — в конец при asc, в начало при desc
- **FR-008**: Сортировка должна применяться после фильтрации (status, tag, search)
- **FR-009**: Сортировка не должна изменять порядок задач в файле хранилища
- **FR-010**: Сортировка должна быть стабильной: при равных ключах сортировки сохраняется порядок из файла
- **FR-011**: При отсутствии параметра сортировки (None) сортировка не применяется
- **FR-012**: Функция не должна добавлять новые внешние зависимости
- **FR-013**: Backend валидирует значения `sort_by` и `sort_order`: при недопустимом значении выбрасывает `ValueError` с описательным сообщением
- **FR-014**: `list_tasks` propagates исключения из `json.load` при повреждённом `tasks.json`; не скрывает ошибки данных, не возвращает пустой список
- **FR-015**: Сортировка не должна влияять на CLI-контракты (команда `list` работает без изменений)
- **FR-016**: Сортировка не должна добавлять новые внешние зависимости

### Constraints

- **Технические ограничения**: Python 3.11+, стандартная библиотека, Typer, pytest, Tkinter. Никаких сетевых вызовов, MCP, плагинов.
- **Блокировка файлов**: Не требуется. `tasks.json` записывается атомарно через `tmp.replace()`. `list_tasks` читает текущую версию без частичных данных.
- **JSON как состояние**: `tasks.json` хранит состояние между запусками приложения. `list_tasks` не отвечает за его создание или изменение — только за чтение и сортировку.

### Out of Scope

- **CLI**: Команда `list` в CLI не получает параметров сортировки — работает без изменений.
- **GUI**: GUI делегирует сортировку backend и не реализует её самостоятельно.
- **Multi-column sort**: Сортировка только по одному полю одновременно.
- **Сортировка по `created_at` в GUI**: GUI не предоставляет интерфейс для сортировки по `created_at` (колонки: Название, Статус, Срок, Теги).

### Key Entities

- **Task**: Задача с полями id, title, status ("todo"|"done"), created_at (ISO UTC), due_date (опционально, ISO UTC), tags (список строк)
- **SortCriterion**: Критерий сортировки — одно из: "title", "status", "due_date", "created_at", "tags", None
- **SortDirection**: Направление сортировки — "asc" или "desc"

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Запрос списка задач с любым допустимым сочетанием фильтров и сортировки возвращает корректно отсортированный список
- **SC-002**: Повторный запрос без сортировки возвращает исходный порядок задач из файла (хранилище не изменяется)
- **SC-003**: При равных ключах сортировки порядок задач совпадает с порядком в файле (стабильность)
- **SC-004**: Запрос списка из 1000 задач с сортировкой выполняется менее чем за 1 секунду на локальном хранилище
- **SC-005**: Сортировка по "title" корректно упорядочивает строки, содержащие кириллицу и латиницу

## Assumptions

- Сортировка по "tags" использует только первый тег задачи (не все теги одновременно)
- При desc для полей с None-значениями (due_date, tags) задачи без значения идут в начало списка
- Case-insensitive сортировка по "title" использует casefold для корректной работы с кириллицей
- CLI не получает параметров сортировки — команда `list` в CLI работает без изменений
- Сортировка по "created_at" опирается на лексикографическое упорядочивание ISO-строк (UTC, суффикс Z)
- GUI не предоставляет интерфейс для сортировки по `created_at` — доступные колонки: Название, Статус, Срок, Теги
- `tasks.json` хранит состояние между запусками приложения; `list_tasks` не отвечает за его создание или изменение

## Clarifications

### Session 2026-11-01

- Q: Должен ли backend проверять значение `sort_by` и `sort_order` и выбрасывать исключение при недопустимом значении, или он должен молча игнорировать невалидные параметры? → A: Backend валидирует и выбрасывает `ValueError` при недопустимом значении (FR-013)
- Q: Что должен делать `list_tasks`, если `tasks.json` повреждён (невалидный JSON) — propagates исключение из `json.load` или возвращает пустой список? → A: Propagates исключение (FR-014). Текущая реализация в `storage.py` не ловит исключения в `list_tasks`.
- Q: Нужна ли блокировка файлов (file lock) при вызове `list_tasks`, чтобы избежать чтения во время записи (`save_tasks`)? → A: Lock не нужен. `tasks.json` записывается атомарно через `tmp.replace()`, что гарантирует целостность чтения (Constraints).
