# Design

## Context

Мотивация — proposal.md; поведение — specs/desktop-task-management/spec.md.
`app.py` связывает Typer с `Task.new` и Storage. `Storage.load` создаёт отсутствующий
файл; `list_tasks(status, tag, search)` фильтрует задачи в порядке JSON. `add_task`,
`edit_task` и `mark_done` используют save_tasks с атомарной заменой и snapshot.
`undo(steps)` восстанавливает общие snapshots; `validate_file(path)` возвращает
`{ok, issues, counts}` без записи. `mark_done` и `edit_task` возвращают None
при неизвестном ID, но повторная отметка done делает запись, поэтому UI блокирует её.

Task.new не проверяет название и дату. STYLE_GUIDE и validate.py требуют ISO UTC
по ISO_FORMAT, хотя CLI принимает строку без проверки. UI проверяет только новый
ввод, не исправляя старые значения. `edit_task` различает None («не менять»)
и строку/список («изменить»); удаление срока через None невозможно.
task-search сохраняет контракт; sort-tasks-by-title не реализован и не является
зависимостью UI. Сортировочных элементов, включая клики по headings, не добавляем.

AGENTS.md ограничивает продукт CLI. Пользователь запросил desktop UI; при apply
нужно отразить это точечное расширение в AGENTS.md, сохранив правила хранения.
Текущий python3 — Homebrew Python 3.14; попытки импорта tkinter и запуска pytest
неуспешны из-за отсутствия `_tkinter` и pytest. Оконные проверки пока не выполнялись.

## Goals / Non-Goals

**Goals:**
- Новый адаптер существующего продукта без дублирования файловой логики.
- Контроллер проверяется без окна; реальные виджеты покрываются коротким smoke-сценарием.
- Различать ошибки записи и ошибки перечитывания после успешной записи.

**Non-Goals:**
- Новый сервисный framework, HTTP, универсальный repository и изменение Storage.
- Новый валидатор данных или автоматическое восстановление файла: используем
  существующий validate_file без расширения его гарантий.
- Конкурентное редактирование несколькими процессами с блокировками и транзакциями.
- Удаление задач, очистка срока, сортировка, календарь и преобразование часовых поясов.

## Decisions

### 1. Один модуль и отдельный запуск

Добавить `src/taskhub/gui.py`: тонкий `TaskController`, главное окно `TaskHubWindow`,
общая форма `TaskForm` на Toplevel и main с защитой `if __name__ == "__main__"`.
Конструктор контроллера принимает
Storage; окно принимает контроллер. Tk/ttk импортировать при создании UI,
чтобы импорт контроллера и headless-тесты не требовали Tcl/Tk. Ни CLI, ни модель,
ни Storage не импортируют gui. Импорт модуля не создаёт окно и не пишет файлы.

Выбран Tkinter/ttk из запроса пользователя; PySide6 добавил бы крупную зависимость.
Новый сервисный framework для адаптера готовых операций не нужен.

### 2. Прямой Python-контракт над существующими операциями

| Метод контроллера | Результат и ошибки | Делегирование |
|---|---|---|
| `list_tasks(status=None, tag=None, search=None) -> List[Task]` | Актуальная выборка, исходный порядок | `Storage.list_tasks` с теми же фильтрами |
| `add_task(title: str, due_date=None, tag=None) -> Task` | Непустой title.strip, проверка непустого срока | `Task.new`, затем `Storage.add_task` |
| `mark_done(task_id: str) -> Optional[Task]` | Обновлённая задача или None при отсутствии | `Storage.mark_done` |
| `edit_task(task_id: str, title=None, due_date=None, tag=None) -> Optional[Task]` | Неотмеченные поля как None; отсутствие ID как None | `Storage.edit_task` |
| `undo(steps: int = 1) -> int` | Ограничение 1–3 до вызова; ValueError при нехватке истории | `Storage.undo` |
| `validate_tasks() -> dict` | Неизменённый отчёт ok/issues/counts или исключение чтения | `validate_file(storage.path)` |

В add пустой срок преобразуется в None, пустой тег — в []; непустой тег — в [tag].
В edit tag=None оставляет список, tag="" передаёт [], непустой tag — [tag].
Не выполнять trim тегов или поисковых строк: точность соответствует Storage.
Изменяемый title обрезается по краям и проверяется; edit без полей отклоняется
до Storage, чтобы не создавать лишний snapshot. Переданный срок в edit не может
быть пустым. Для нового непустого срока проверить datetime.strptime с ISO_FORMAT
и точное обратное форматирование: это фиксирует шесть цифр микросекунд и Z.
Старый некорректный срок, не выбранный для изменения, передаётся как None и сохраняется.
Это ограничения только GUI-ввода: CLI, Task и Storage не меняются.

Контроллер не содержит виджетов и не оборачивает файловые исключения в успех.
UI ловит ожидаемые ошибки OSError, ValueError (включая JSONDecodeError), TypeError
и KeyError на границах операций, показывает русское описание с деталями ошибки.
Ошибки структуры, не обрабатываемые существующим валидатором (например, TypeError),
также показываются как ошибка проверки, не как успешный отчёт.
Это не добавляет новую валидацию модели или нормализацию существующих данных.
Альтернатива — вызывать функции Typer/парсить CLI-stdout — отвергнута: это смешало бы
разные представления, пути и обработку ошибок.

### 3. Простая компоновка окна

Название окна «TaskHub». Сверху — абсолютный путь `Storage.path`, Entry поиска,
Combobox статуса с «Все», todo, done (readonly), Entry точного тега,
«Применить» и «Сбросить»;
основная область — ttk.Treeview с headings, одиночным выбором и вертикальной
прокруткой. Treeview iid — полный Task.id, а не индекс/название. Колонки:
«Название», «Статус», «Срок», «Теги»; значения берутся из Task без изменения объектов.
Снизу — «Добавить», «Изменить», «Выполнено», «Обновить», readonly выбор 1–3
(default 1), «Отменить изменения», «Проверить данные» и строка состояния.
Проверка открывает read-only прокручиваемый отчёт со всеми issues и доступными
счётчиками, не ограниченный размером строки состояния.
Контейнеры растягиваются при изменении окна; кастомные темы и иконки не нужны.

UI хранит последний успешно загруженный список и отдельно активную тройку фильтров.
Редактирование полей поиска не применяет их до «Применить». «Сбросить» очищает
поля и активные фильтры, сразу перечитывает полный список. Refresh и мутации
используют активную тройку, не несохранённый ввод фильтров.
Каждая успешная перезагрузка полностью заменяет строки и сбрасывает selection;
в статусе — число показанных задач, «Нет задач» без фильтров или «Ничего не найдено»
с фильтрами. «Добавить» и undo доступны при исправном списке, edit — при любом
выборе, done — только для выбранной todo. Undo при пустой истории не отключаем:
достоверный ответ даёт Storage, UI показывает его ошибку.
«Обновить», фильтры и «Проверить данные» доступны также при ошибке загрузки.
Обновление только при старте, после записи и по кнопке; polling не нужен.

### 4. Общая форма добавления и редактирования

TaskForm — небольшое модальное Toplevel с полями названия, срока и одного тега,
«Сохранить»/«Отмена». В add название обязательно, срок и тег необязательны.
В edit у каждого поля отдельный Checkbutton «Изменить», по умолчанию выключенный;
поле доступно после включения, до этого title/due показывают текущие значения.
Поле одного тега изначально пусто и подписано «Заменить все теги»; текущие теги
видны в таблице. Никакой неявной потери нескольких тегов при изменении названия.
Изменяемые поля преобразуются по контракту контроллера, остальные передаются None.
«Отмена»/закрытие формы ничего не записывает; ID, статус и created_at не редактируются.
Под сроком подсказка ISO UTC и пример, без календаря. Старый срок можно увидеть
и оставить без изменения; очистка срока явно отклоняется. Форма запоминает ID
выбранной задачи, не ищет её по названию или текущему selection после открытия.

### 5. Обработка операций без оптимистических изменений

Вызовы синхронны в Tk mainloop: для маленького локального файла это минимальная
достаточная реализация. Сначала запись, затем отдельная фаза refresh, без добавления
строк/изменения статуса до подтверждения Storage.

- Ошибка add/edit: форма открыта, значения сохраняются, показана ошибка.
- Успех add/edit: форма закрывается сразу после возврата Storage, затем refresh.
- Успех done/undo: refresh с активными фильтрами; при undo сообщить число шагов.
- Неизвестный ID в done/edit: «Задача не найдена. Обновите список», без успеха.
- Ошибка refresh: очистить таблицу, отключить add/edit/done/undo, показать ошибку; повторить
  можно через «Обновить». Ошибка стартового чтения не закрывает уже созданное окно.
- Если запись успешна, а refresh неуспешен: отдельное сообщение «Изменение сохранено,
  но список не удалось обновить», без предложения повторить запись.
- Локальная ошибка пустого названия: «Введите название задачи», без вызова Storage;
  edit без полей — «Выберите поля для изменения». Некорректный срок, попытка его
  очистки и нехватка истории — отдельные понятные сообщения.
- Проверка данных не вызывает refresh/init и не зависит от фильтров. Отсутствующий
  файл, некорректный JSON или исключение валидатора — ошибка проверки; ok=false —
  отчёт со всеми issues; ok=true — успешный отчёт со счётчиками всего файла.
  Проверка не меняет состояние доступности мутаций: восстановление через refresh.

Не обещаем rollback при сбое записи: механизм Storage остаётся прежним, snapshot
может уже существовать. UI сообщает факт ошибки, а не гарантирует транзакционность.

### 6. Рабочий каталог и запуск

main создаёт `Storage(Path.cwd().resolve())`. Отдельный выбор файла/параметр root
не нужен: запуск из корня workspace разделяет tasks.json с CLI. Документация
показывает запуск из корня ITMOv2 с `PYTHONPATH=practices/practice_04/src`.
Отсутствующий файл инициализируется через прежний Storage.load при чтении.

Таблица запуска новой точки входа; существующие Typer-команды не меняются:

| Вызов | Условия | Ожидаемый stdout/stderr | Код выхода |
|---|---|---|---|
| `python -m taskhub.gui` | Доступны Tcl/Tk и графическая сессия | stdout/stderr пусты; интерактивные ошибки внутри окна | 0 после обычного закрытия |
| `python -m taskhub.gui` | Нет Tcl/Tk или нельзя создать Tk root | stdout пуст; stderr с понятной причиной невозможности запуска | Ненулевой |

Только main обрабатывает ImportError при загрузке Tk и TclError при создании окна;
при таком сбое хранилище ещё не читается и не создаётся. При обычном закрытии
destroy завершает mainloop, фоновых потоков нет. Не добавляем entry point в Typer.

### 7. Проверки

TDD: сначала тесты контроллера с реальным Storage в tmp_path, затем минимум кода.
Проверять title.strip, сроки/теги add и edit, неизменность невыбранных полей,
пустой ввод/отмену/no-op без изменения байтов/истории, разные ID одинаковых названий,
done/edit miss и сохранение после нового экземпляра Storage. Для поиска переиспользовать
кейсы task-search: casefold, кириллица, литеральные пробелы, AND, пустой результат
и порядок. Сравнивать ID и байты/историю до/после чтения, reset и validate.
Undo: 1 и 3 шага, недостаточная история, ограничения 0/4 до вызова Storage,
восстановление add/done/edit и изменений из CLI. Для нескольких snapshots тесты
должны управлять временем, избегая совпадений timestamp существующего Storage.
Проверка данных: ok, version/даты/duplicate ID, missing file, broken JSON;
гарантии валидатора не расширять. Ошибки записи — исключения через monkeypatch.

Отдельные оконные тесты в том же tests/test_gui.py с локальным fixture: импорт Tk
и попытка создать root; при недоступности среды skip с причиной, без пропуска
контроллерных тестов. С реальными widgets и tmp_path проверить нажатия кнопок,
disabled-состояния, применение/сброс фильтров, пустой список против пустой выборки
и ошибки, формы add/edit и отмену, закрытие формы после успешной записи,
выбор шагов undo и отчёт проверки даже при сломанной таблице. Покрыть успешную
запись с ошибкой перечитывания и восстановление через refresh; done/edit/undo
сохраняют активные фильтры, изменённая задача может исчезнуть из выборки.
Не использовать долгоживущий mainloop в тестах: invoke/update и destroy в finally.

Обязательные проверки при apply: полный `python -m pytest -q`, `python tools/lint.py`
из practice_04, а также ручное открытие окна в Tk-совместимом окружении. Пропущенный
оконный тест не является доказательством работающего UI: демо и визуальная приёмка
всё равно нужны. Внешний CLI-сценарий использует временный каталог, не tasks.json
пользователя. Вход без Tcl/Tk проверять изолированным subprocess/имитацией отказа
импорта, вместе с доступностью прежнего CLI и отсутствием записи при импорте gui.

## Risks / Trade-offs

- [Нет Tcl/Tk у выбранного Python] → предварительно проверить интерпретатор;
  документировать системную предпосылку, не добавлять tkinter в pip dependencies.
- [Синхронный IO замораживает окно на больших файлах] → принять для локального
  малого хранилища; потоки рассматривать отдельным изменением при реальной потребности.
- [Пользователь запускает UI из другого каталога] → показывать абсолютный путь
  и документировать совместный рабочий каталог с CLI.
- [Несколько тегов случайно заменяются одним] → явный флажок изменения и подпись
  «Заменить все теги», неизменённое поле всегда передаётся None.
- [Undo понимается как отмена только видимой задачи] → подпись/подсказка, что
  откатываются последние изменения всего файла, включая CLI, независимо от фильтров.
- [Файл меняется извне] → явная кнопка обновления и обработка miss; блокировки,
  строгую защиту от гонок и слияние изменений этот интерфейс не обещает.
- [Тесты контроллера зелёные, виджеты не запускались] → отдельно сообщать skips
  и требовать фактическое оконное демо при приёмке реализации.

## Migration Plan

Данные мигрировать не нужно. При apply добавить gui.py, тесты и инструкции запуска,
обновить описание архитектуры в AGENTS.md. Приёмка на временном хранилище:
пустой список → добавить со сроком/тегом → поиск/фильтры → edit → done → undo
на 1–3 шага → проверка данных → перезапуск и CLI/refresh. Затем ошибки пустого
ввода/даты, отсутствующего ID, нехватки истории и повреждённого JSON с восстановлением.
Откат поставки — удалить новую точку входа и связанные документы/тесты;
созданные задачи остаются совместимы с CLI. Sync/archive — после приёмки человеком.
