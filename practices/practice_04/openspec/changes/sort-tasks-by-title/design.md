# Design

## Context

Мотивация описана в proposal.md. Сейчас `app.py:list` получает задачи через
`Storage.list_tasks(status, tag, search)` и сразу печатает их в полученном порядке.
Storage фильтрует записи JSON последовательно, не меняя их относительного порядка.
`get_storage()` вызывает init, поэтому даже чтение может создать отсутствующий tasks.json.

Спецификация task-search закрепляет API Storage и равенство порядка CLI/Storage.
Delta task-search уточняет последнее только для вызовов без явной сортировки.
Дизайн фиксирует выбор слоя сортировки и порядок проверки опции до автоинициализации.

## Goals / Non-Goals

**Goals:**
- Добавить сортировку представления на границе CLI без расширения Storage API.
- Не затрагивать файловые операции; использовать существующие фильтры и форматтер строк.
- Проверять новую опцию до `get_storage()` и любых действий с данными.

**Non-Goals:**
- Переносить сортировку в хранилище, модель или MCP.
- Менять обработку некорректных данных и ошибок чтения, добавлять локаль или нормализацию.

## Decisions

### 1. Сортировка результата в CLI

После существующего `st.list_tasks(...)` при `sort == "title"` применить
`sorted(tasks, key=lambda task: task.title.casefold())` к локальному списку.
Встроенная стабильная сортировка сохраняет порядок равных ключей. Это преобразование
представления не выполняет файловых операций и не меняет объекты задач.

Альтернатива: параметр sort у Storage. Отклонён, поскольку расширяет публичный API
и область изменения без необходимости; прямые вызовы Storage и MCP сохраняют свой порядок.
Дополнительный слой или зависимость для одного ключа не нужны.

### 2. Проверка значения до получения хранилища

Добавить необязательную строковую опцию `--sort` с default None и описанием `title` в help.
В начале команды отклонять любое значение, кроме None и точной строки `title`:
диагностика через `typer.echo(..., err=True)`, затем `typer.Exit(code=1)`.
Отсутствующее значение опции обрабатывает парсер Typer до вызова функции.
Конкретный текст ошибки не является контрактом.

Альтернатива: enum для одного значения. Явная проверка проще и соответствует
существующему стилю Optional и typer.Exit. Проверка после get_storage отклонена:
иначе неверная опция могла бы создать tasks.json.

### 3. CLI-поведение: таблица контракта

| Вызов | Условия | Ожидаемый stdout/stderr | Код выхода |
|---|---|---|---|
| `list` | tasks.json содержит Zulu, alpha, Beta в указанном порядке | stdout: строки задач в порядке Zulu, alpha, Beta; stderr пуст | `0` |
| `list --sort title` | tasks.json содержит Zulu, alpha, Beta в указанном порядке | stdout: строки задач в порядке alpha, Beta, Zulu; stderr пуст | `0` |
| `list --sort title` | Задачи Straße, STRASSE, strasse с одинаковыми ключами casefold | stdout: строки задач с сохранением исходного относительного порядка | `0` |
| `list --status todo --tag учеба --search практика --sort title` | Заданы все три фильтра | stdout: только выбранные по всем фильтрам задачи, упорядоченные по названию | `0` |
| `list --sort title` с соответствующими фильтрами, если нужны | Пустой результат | stdout пуст, без поясняющих строк | `0` |
| `list --sort priority`, `list --sort Title`, `list --sort ""`, `list --sort` | Неподдерживаемое или отсутствующее значение | stdout пуст; stderr: диагностика | Ненулевой |
| `list --sort title` | tasks.json отсутствует | stdout пуст; создаётся прежнее пустое хранилище версии 1 без истории | `0` |

Формат строк сохраняется: `<id> [status] title (due=... tags=...)`.
Успешный вызов с существующим tasks.json сохраняет его байты и snapshots истории.
Ошибочные вызовы из таблицы не создают отсутствующее хранилище и не меняют
существующее хранилище или историю.
Новая сортировка не вызывает save_tasks или _write.

### 4. Проверки по существующему образцу

Добавить `tests/test_sort.py` с CliRunner и временным хранилищем по образцу
`tests/test_search.py`. Сравнивать полный stdout с ожидаемыми строками и порядком id,
а не только наличие названий. Проверить кириллицу и casefold-эквивалентные строки.
Для проверки отсутствия записи сравнить байты tasks.json и имена/байты snapshots
до и после; проверить как существующую историю, так и её отсутствие.

Существующие тесты поиска и Storage остаются регрессией старых вызовов.
Реализация идёт через red → green, затем весь pytest и проектный линтер.

## Risks / Trade-offs

- [Unicode-порядок отличается от словарного] → явно задать casefold и отсутствие локали;
  проверять конкретные примеры, не обещать языковую сортировку.
- [Лишняя копия списка и O(n log n)] → приемлемо для текущего локального JSON-списка;
  по умолчанию сортировка не выполняется.
- [Неверная опция создаёт хранилище] → валидировать до get_storage и покрыть тестом.
- [Противоречие старой spec о порядке] → включить две точечные правки task-search
  в этот change, оставив исходный контракт для вызовов без --sort.

## Migration Plan

Миграция данных не требуется. После приёмки документов реализовать change,
проверить CLI и тесты, дополнить PROJECT_README.md примером.
Откат реализации — убрать CLI-опцию и сортировку; сохранённые данные не меняются.
Sync и archive выполняются после отдельной приёмки результата человеком.
