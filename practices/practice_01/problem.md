# Проблема и метрики

## Проблема

- Пользователь: инженер-ревьюер PR
- Ситуация: отправляет diff в сервис, чтобы получить подсказки по рискам и проверкам
- Что происходит сейчас: сервис пересылает diff во внешний LLM без редактирования секретов, без лимита размера, без таймаута и возвращает несоответствующий формату ответ
- Почему это мешает пользователю или бизнесу: риски утечки секретов (SEC-1), нестабильность и подвисания (REL-1), отсутствие предсказуемого API-ответа (OUT-1), невозможность корректно обрабатывать большие PR (API-1)
- Что не входит в задачу: автоматический merge/approve, генерация кода, любые действия в GitHub (SCOPE-1)

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля ответов в требуемом формате (OUT-1) | < 20% по ручной проверке тренировочного diff | >= 95% | после внедрения формата | интеграционные тесты |
| Ошибки по таймауту внешнего LLM | Нерегламентировано | ≤ 1% запросов; ошибки превращаются в контролируемый ответ | на стенде и в CI | логи сервиса (без содержимого diff) |
| Отклонение слишком длинных diff | Не реализовано | 100% diff > 20k символов отклонены 413 | в тестах и нагрузочном прогоне | e2e и интеграционные тесты |
| Утечки секретов в prompt | Потенциально присутствуют | 0 обнаруженных утечек при тестовом токене | на каждом релизе | юнит и e2e проверки редактирования |

## Почему изменение метрики подтвердит решение проблемы

Метрики напрямую отражают выполнение правил SEC-1, API-1, REL-1 и OUT-1. Их достижение означает, что сервис безопасно обрабатывает вход, стабильно отвечает в срок и возвращает предсказуемый результат.

- Для чего: сформулировать проблему и измеримые метрики, связанные с правилами кейса
