# Анализ процесса: AS IS и TO BE

## AS IS

Ревьюер формирует diff и отправляет его в FastAPI. Сервис без проверок передаёт весь diff во внешний LLM и возвращает сырой текст ответа как комментарий. Нет редактирования секретов (риск SEC-1), нет отсечки больших diff (API-1), нет таймаута и graceful error (REL-1), нет нормализованного формата результата (OUT-1). Логи потенциально могут содержать чувствительные данные, если добавить логирование тела (OBS-1 запрещает).


## TO BE

Сервис принимает diff, валидирует длину, редактирует потенциальные секреты, формирует строгий prompt, вызывает LLM с таймаутом 10 секунд. На ошибки возвращает контролируемый ответ. Результат нормализуется к OUT-1: summary, до трёх risks с file/line/evidence/risk, checks[]. Логи содержат только request_id, длительность и статус.

```mermaid
flowchart LR
    A[POST /api/reviews] --> B[Валидировать размер diff (API-1)]
    B -->|<=20k| C[Редактировать секреты (SEC-1)]
    B -->|>20k| E[HTTP 413]
    C --> F[LLM call timeout 10s (REL-1)]
    F --> G[Нормализовать OUT-1]
    G --> H[Ответ summary/risks/checks]
```

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Безопасность ввода | Секреты могут утечь | Секреты редактируются | юнит-тесты редактирования + e2e |
| Надёжность ответа | Подвисания возможны | Таймаут 10с и graceful error | интеграционные тесты с симуляцией таймаута |
| Предсказуемость формата | Сырой текст | Строгая схема OUT-1 | контрактные тесты схемы |
| Работа с большими PR | Не ограничено | 413 для >20k | e2e граничного размера |
